# 设计评审：每日 AI 新闻助手

评审日期：2026-10-12（Australia/Sydney）。基线提交：`eeb8210`。范围：原设计、README、`app/`、测试及启动/建表配置。仓库没有原始题目，无法确认额外评分细则。本文不表示下列代码问题已经修复；修订方案见 [DESIGN.md](DESIGN.md)。

## 结论

现有手写 Agent、Provider 适配、文件工具和 trace 构成清晰的演示基础，保留这些选择。主要不足是把“模型结束并写出文件”近似为“完成每日新闻服务”：内容质量、历史记忆、运行受理、按时生成与邮件交付还没有各自的验收契约。

建议先补交付闭环，再做一个主扩展：**带证据、推荐理由和历史对照的事件更新雷达**。它能体现长期使用价值，无需先增加多 Agent 或向量数据库。

P1 表示影响核心结果可信度或交付正确性，应优先补齐；P2 表示下一轮应改善。联网与共享访问问题另注明适用门槛，不把全部生产基础设施都当作本地演示的前提。

## 1. P1：成功判定不包含新闻质量

**证据**：[service.py](../app/service.py#L50) 的 `ok` 只检查停止原因和 `_wrote_this_run()`；[agent.py](../app/agent.py#L18) 要求 5–10 条，未校验引用、时效、相关性和事件重复。

**影响**：任意非空正文也可能成功；无新增、来源故障和可信简报没有独立的内容结果。固定条数可能诱使模型补写弱相关内容。

**建议**：结构化草稿、工具生成的证据 ID、程序验证、统一渲染；允许 0 条，区分无新增与来源失败。事实支持度另做人工标注评测，不能把“有链接”当成“事实正确”。验收见设计 §4、§13。

## 2. P1：按日覆盖丢失去重记忆，“不可变”没有权限保证

**证据**：[service.py](../app/service.py#L52) 每次成功覆盖 `briefs/<日期>.md`，Prompt 只引导查该目录；[fs_tools.py](../app/tools/fs_tools.py#L55) 可覆盖工作区任意文件，包括旧 `runs/` 和画像。

**影响**：同日 A → B → 再次检索 A 时，A 已从查重视图消失。独立文件名仅隔离正常运行目标，不能阻止 Agent 改历史。

**验证**：本次在临时目录调用现有文件工具并执行与 Service 相同的 `copyfile`，确认覆盖后 A 返回 `no matches`；也确认旧运行文件可被覆盖。没有修改真实用户数据。

**建议**：成功历史追加保存，建立条目索引；模型只写本轮 staging，Service 持有发布权限。先修存储语义，再做事件级去重。验收 A → B → A 不重复发布 A。

## 3. P1：请求受理与运行终态缺少可靠记录

**证据**：[main.py](../app/main.py#L92) 启动 daemon 线程即返回 `started`，异常只进日志；[service.py](../app/service.py#L39) 初始化和执行 Agent 后才插入 `Brief`。

**影响**：初始化失败、锁拒绝、进程中断可能没有记录，用户仍看到“已开始”。单用户锁不限制全局手动线程数量。

**建议**：先创建持久 run，再提交统一有界执行池；重复请求返回当前 run，异常和重启中断都有终态。明确文件与 DB 提交间的恢复策略，不宣称跨系统原子性。见设计 §7。

## 4. P1：每日时间与漏跑恢复没有完整业务语义

**证据**：[scheduler.py](../app/scheduler.py#L9) 默认调度器启动后从用户配置重建 cron；[service.py](../app/service.py#L42) 使用 `date.today()`。没有用户时区、日期幂等键和漏跑扫描。

**影响**：迁移主机时区后用户的“08:00”和业务日期可能改变；错过时间后重启，不保证当天补跑。误触发宽限不代替业务漏跑账本。

**建议**：IANA 时区、统一业务日期、开始生成时间、补跑窗口、DST 策略和定时幂等键共同设计。判断结合当前代码与 [APScheduler 3.x 文档](https://apscheduler.readthedocs.io/en/3.x/userguide.html#missed-job-executions-and-coalescing)，不能仅凭已有调度参数宣称可靠交付。

## 5. P1：生成与投递混用结果

**证据**：[service.py](../app/service.py#L59) 提交简报后发送邮件，失败拼入 `stopped_reason`；[service.py](../app/service.py#L79) 在 SMTP 全局关闭时静默返回。

**影响**：用户开启邮件但服务未配置时没有可见投递结果；生成成功不证明发送，重新生成来补发既增成本也可能重复。

**建议**：独立投递记录，事务内创建待发送项，失败只重试原正文。区分 disabled、pending、sent、failed 和结果不确定；SMTP 接受后的崩溃窗口不能保证 exactly-once。见设计 §10。

## 6. 条件 P1：真实网络与共享访问边界不足

**证据**：[news_tools.py](../app/tools/news_tools.py#L110) 只检查 URL 前缀并自动跟随重定向；[main.py](../app/main.py#L56) 以邮箱查身份，用户和简报路由无鉴权；[run.sh](../run.sh#L8) 监听 `0.0.0.0`。

**影响**：外部内容可诱导抓取内网；能访问服务的人可查看或操作他人资源。bash 白名单不能保护 HTTP 入口与 Web 资源授权。

**建议**：真实抓取前完成 SSRF 防护与下载限额，本地默认 loopback；共享前完成认证、对象授权、CSRF、限流与邮箱验证。DNS/重定向边界参照 [OWASP SSRF 指南](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)，完整方案见设计 §6、§12。

## 7. P2：轮数和截断不等于资源预算

**证据**：[agent.py](../app/agent.py#L45) 限模型轮数，但每轮可有多个工具调用，重复检测按原始参数字符串；[registry.py](../app/tools/registry.py#L59) 在执行后截断；[news_tools.py](../app/tools/news_tools.py#L113) 在获取完整响应后截断。

**影响**：15 轮不能推导总工具次数、时长、下载量和 token 上限；等价参数的不同序列化也不会视为重复。

**建议**：统一 RunContext 管理调用数、期限、token 与字节预算，参数规范化去重，全局限流。底层不能取消同步调用时，不宣称硬超时。见设计 §11。

- RSS 内部 feed 错误会静默跳过，不能声称全部来源错误都回传。

- 删除“固定流水线不能回退”“每次 trace 都不同”；自主换源需真实模型证据。
- 不沿用“29 个测试约 1 秒”；转换测试与模型质量验收分开。
- `create_all` 只建缺失表，不能当迁移；SQL 文件与 ORM 非严格等价。
