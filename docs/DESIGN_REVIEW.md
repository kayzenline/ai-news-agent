## 2. P1：核心结果与交付缺口

### R1：来源状态记录已实现，覆盖与持久化仍不完整

**已实现**：[news_tools.py:253](../app/tools/news_tools.py#L253) 返回带来源健康信息的 `SearchResult`；[registry.py:138](../app/tools/registry.py#L138) 记录 `SearchRecord`，全部来源失败返回工具失败；[service.py:209](../app/service.py#L209) 要求本轮至少一次成功来源检索，才允许空草稿记 `no_news`，否则记 `insufficient_search`。`0f7c443` 及 `test_zero_search_empty_draft_is_marked_failed`、`test_all_sources_failed_returns_false_and_cannot_be_no_news`、`test_successful_search_with_no_hits_allows_valid_no_news` 覆盖原反例与正常空结果。

**剩余证据**：[evidence.py:82](../app/evidence.py#L82) 只判断任意检索来源成功，不验证用户各话题覆盖；[evidence.py:104](../app/evidence.py#L104) 的归档只包含 Evidence，未保存内存中的 `searches`。RSS 账本按来源组统计，[news_tools.py:297](../app/tools/news_tools.py#L297) 在任一 feed 报错且没有返回条目时将 RSS 整体记失败，不能区分“其他 feed 请求成功但正常为空”；有条目时也不会在 `sources_failed` 内完整记录部分 feed 失败，错误仅留在搜索文本。[brief.py:147](../app/brief.py#L147) 对有条目的简报不渲染顶层 `note`，也没有来源覆盖提示。

**影响**：零检索和全部故障已不再直接展示“无新闻”。不过单个来源成功即可满足门槛，仍可能漏检话题；部分来源失败、背景说明及检索覆盖无法在最终正文完整辨认或从结构化归档复核。

**建议与验收**：保留现有成功检索门槛，完善逐 feed 的成功/空结果/失败及话题覆盖账本并持久化；部分成功且有合格条目应展示覆盖不足。补测“一 feed 失败、其余成功为空”“部分失败且有新闻”和“仅覆盖部分话题”，并验收有新闻时仍保留必要说明。对应设计 §4、§9、§11。

### R2：日期限制没有成为发布条件

**证据**：[news_tools.py:32](../app/tools/news_tools.py#L32) 只检查日期下界，没有未来上界；[brief.py:32](../app/brief.py#L32) 的校验不检查证据日期或草稿中的“今日发布”。

**历史复核 / 当前核对**：上一轮临时反例中，2001 年、2099 年和未知日期的证据均可通过草稿校验；本轮静态核对未见发布侧日期校验。旧日期通过校验器并不表示所有搜索适配器都会返回旧文；问题是直接抓取、来源异常时间和模型表述没有发布侧约束。

**影响**：有真实链接的旧消息或未来时间仍可成为“每日新闻”。未知日期的来源标签已经展示，不能把这一展示能力也写成未实现。

**建议与验收**：区分来源发布时间、事件时间与抓取时间；未来时间拒绝或标异常，旧材料仅作背景，未知日期不得宣称今日发布。HN 提交时间不能代替原文发布时间。用已知旧文、未来日期、未知日期与同日新文验收。对应设计 §4、§9。

### R3：数据库提交失败会污染去重历史

**证据**：[service.py:201](../app/service.py#L201) 在提交 Brief 前发布正文和历史；[service.py:261](../app/service.py#L261) 才提交数据库；[service.py:157](../app/service.py#L157) 下一轮从文件历史建立已发布 URL 集合。

**历史复核 / 当前核对**：上一轮在临时库中注入发布后提交异常，得到 Brief 行数 0、历史文件数 1；重试同条新闻时被判 `already published`，最终 `validation_failed`。本轮确认文件先写、DB 后提交的顺序仍在，未重新执行该故障注入；现有历史隔离测试没有覆盖这个窗口。

**影响**：用户没有可查看的成功简报，该新闻却已被去重。正文、历史、草稿/证据 JSON 各自落盘，也不是整体原子发布。

**建议与验收**：以已提交的简报记录作为发布事实来源，历史视图可重建；设计文件准备、DB 提交与恢复对账协议，清理或回滚未提交历史。注入发布各步、DB commit 前后故障，保证重试可发布且账本/文件一致。对应设计 §7、§8。

### R4：同一投递记录并发执行会重复发信（原反例已修复）

**历史问题**：上一轮 `f8f815b` 在首个模拟 SMTP 调用阻塞时，用第二个线程执行同一 Delivery，共发送两次，最终 `sent/attempts=2`。唯一行和稳定 Message-ID 未阻止并发发送。

**当前修复**：`0f7c443` 在 [service.py:312](../app/service.py#L312) 用数据库条件更新领取 `pending/failed/unknown`，只有领取成功的调用进入 SMTP；`sending` 或 `sent` 不会再次领取。`test_concurrent_deliver_claims_atomically` 验证两个并发调用只有一个 SMTP 调用，`test_delivery_is_separate_from_generation` 继续覆盖已发状态跳过。

**剩余边界**：该修复解决应用内同记录并发领取，不构成端到端 exactly-once。SMTP 可能已接受但进程尚未记 `sent` 时崩溃，仍需保留 `unknown` 和用户显式重发语义；自动投递与对账缺口另见 R10。

**验收状态**：并发领取回归已加入并纳入本轮离线套件；真实 SMTP 与进程崩溃边界本轮未验收。对应设计 §10.2。

### R5：失败定时记录阻止当天恢复执行

**证据**：[service.py:48](../app/service.py#L48) 对已存在幂等键无论终态都返回旧 Run；容量拒绝也保存带键失败记录；[scheduler.py:96](../app/scheduler.py#L96) 只判断当天键是否存在。

**历史复核 / 当前核对**：上一轮队列满时产生 scheduled failed，容量恢复后补跑列表仍为空，同键提交仍返回旧失败；初始化失败行为相同。本轮静态核对该行为未变。现有 `test_business_date_and_catch_up_use_user_timezone` 明确按“有记录便不补跑”断言，尚未覆盖可恢复失败策略。

**影响**：短暂故障会让用户错过当天简报；“每日一个逻辑 run”目前等价于“每日最多一次受理尝试”，中断也不能自动恢复。后续日期使用新键，仍可正常执行。

**建议与验收**：保留一个逻辑 run，引入 attempt 与有界重试策略，区分成功、无新闻、运行中和可重试失败；容量恢复及重启后在窗口内恢复尝试。验收不并发重复执行，同时不把失败当作当天完成。对应设计 §7、§10.1。

## 3. P2：边界与扩展尚未完善

### R6：更新标志不能证明有新事实

[brief.py:76](../app/brief.py#L76) 仅要求 `update` 有非空 delta；[brief.py:96](../app/brief.py#L96) 对更新跳过历史 URL 拒绝。上一轮临时复核中，已发布 URL 加任意 delta、没有新证据或有效事件关联即可通过；一个普通条目混入新 URL 也可通过历史规则。本轮静态核对该规则未变。

应建立旧简报与事件关联，比较新旧证据，允许不确定结果但不能把字段存在当作事件雷达完成。验收公告、转载、实质更新及伪更新；事实支持与订阅相关性另建人工样本集。对应设计 §4、§8、§13。

### R7：不合法字段或 URL 可能跳过工具纠错流程

[brief.py:71](../app/brief.py#L71) 的 `change_type` 未先验证类型：非空列表/对象会抛 `TypeError`，空列表会被当成 `new`；[agent.py:107](../app/agent.py#L107) 未捕获 validator 异常，无法进入修订。

[evidence.py:23](../app/evidence.py#L23) 访问非法端口会抛 `ValueError`；搜索结果中的这类 URL 可以进入证据库，随后 [brief.py:91](../app/brief.py#L91) 规范化引用 URL 时直接抛异常，而非返回校验错误。已有坏 URL 时，后续正常抓取的证据匹配也可抛异常；[registry.py:150](../app/tools/registry.py#L150) 的证据注入位于工具执行异常处理之外。`call_key` 已捕获非法端口的 `ValueError` 并回退参数序列化，不属于此处逃逸路径。合法 IPv6 规范 URL 还丢失主机方括号。这些是上一轮离线反例，本轮确认相应路径仍在；新增字典形式工具参数支持没有替代草稿字段与 URL 校验。

应让所有草稿字段严格校验并返回错误列表，URL 规范化对无效输入产生受控错误且正确保留 IPv6；验收这些输入能反馈给模型修改，而非直接失败。对应设计 §4–6。

### R8：软期限、结束原因和资源预算不完整

[agent.py:78](../app/agent.py#L78) 只在调用前检查期限；最终响应回来后可直接结束。上一轮临时复核中模型耗时超过期限后仍为 `model_finished`，本轮确认该路径未变。这既不是硬截止，也未做到每次响应后的软期限复查。[providers.py:63](../app/llm/providers.py#L63) 对 `content_filter` 等未知结束原因映成正常 `end`，原始诊断丢失。

后续已在 [agent.py:195](../app/agent.py#L195) 对 `max_steps` 时已有草稿校验，并由 [service.py:180](../app/service.py#L180) 允许合格草稿发布；[brief.py:140](../app/brief.py#L140) 添加步数截断提示，未写出合格草稿仍失败。该行为由两项 `test_max_steps_*` 回归覆盖，不能再把所有步数耗尽统一描述为失败。

总 token、文件读取、草稿/磁盘、搜索来源下载和上下文大小均无完整预算；现有输出截断及 `fetch_url` 2 MB 不能覆盖这些入口。[agent.py:163](../app/agent.py#L163) 只归档工具输出前 2,000 字符，模型可能收到更长结果；Evidence 摘录也只保存前 500 字符，不能完整重建模型所见正文。应保留原始结束原因、保存实际输入、复查响应时间并按剩余预算约束 I/O/重试；用超时最终响应、过滤响应和超大输入验收。对应设计 §5、§6、§11。

### R9：补跑窗口和事件时间存在边界

[scheduler.py:89](../app/scheduler.py#L89) 只构造当天到期时刻。上一轮临时复核 Sydney 用户 23:30 到期、翌日 00:20 重启，虽距漏跑仅 50 分钟且窗口 6 小时，仍不会补跑；本轮确认仍只扫描当天。[db.py:76](../app/db.py#L76) 等字段使用无时区 `datetime.now()`，[main.py:152](../app/main.py#L152) 与页面直接显示宿主时间。

应按补跑时间窗口覆盖可能的前一业务日，并为超窗漏跑留记录；事件时间统一 UTC，展示时明确用户时区。用跨午夜、DST 重复/跳过与宿主时区变化验收。当天业务日期和时区 cron 已实现，不应回退成“没有时区支持”。对应设计 §7、§10.1。

### R10：投递挂起与 Run 终态缺少恢复闭环

[service.py:261](../app/service.py#L261) 提交 Brief+Delivery 后发送，最后才由 [service.py:83](../app/service.py#L83) 更新 Run。崩溃可留下成功 Brief、甚至已发邮件，而 Run 重启显示 `interrupted`。[service.py:338](../app/service.py#L338) 启动只处理 `sending`，提交后尚未开始发送的 `pending` 不自动恢复；上一轮临时库确认仍保持 pending，本轮核对无新增自动投递 worker。R4 的原子领取解决并发争用，未改变这些执行与恢复边界。

页面可手动重发 `pending/failed/unknown`，并非无法恢复；`not_configured` 补配 SMTP 后没有重发按钮。应提供 pending 扫描/退避与记录对账，并把发送移出生成执行槽。验收提交后发送前、SMTP 返回后 Run 更新前的崩溃边界。对应设计 §7、§10.2。

### R11：证据最终地址与数据迁移尚不完整

[news_tools.py:401](../app/tools/news_tools.py#L401) 跟随重定向后只返回 PDF 标志与文本；[evidence.py:133](../app/evidence.py#L133) 仍以原请求 URL 存证据和继承搜索日期。应保存请求与最终 URL，并避免继承不匹配页面的时间/标题。验收合法跨站重定向。PDF 文本提取已在 [news_tools.py:374](../app/tools/news_tools.py#L374) 实现，最多读取前 10 页并按字符截断；无 OCR 和解析硬限时。提取异常返回 `ERROR:` 字符串，注册表目前仍可给该结果分配证据并记工具成功，需补失败语义验收。

[db.py:85](../app/db.py#L85) 只建表补列，没有迁移版本、完整约束/索引升级、正文 hash 或条目索引；SQL 文件也非严格等价。应增加版本迁移和旧数据升级验收，不能把 `create_all` 当成迁移系统。对应设计 §4、§7。

### R12：共享部署和长期数据管理仍是计划

[main.py:101](../app/main.py#L101) 到各资源路由没有登录、对象授权或 CSRF；首页输入姓名和邮箱只是建立或查找本地用户，匹配昵称不构成认证。姓名/订阅会进入模型上下文，trace 与错误没有完整脱敏/保留策略；没有删除用户与关联文件清理、备份恢复或 OS 沙箱。

当前 loopback、staging 权限、HTML 清理与公网抓取检查已经实现，应保留；DNS 检查与连接间窗口仍需出口策略补强。公网查询/抓取也没有个人信息外发限制。共享访问前验收越权、CSRF、注入外发、出口规则和删除/恢复；本机演示保持单进程。对应设计 §12。
