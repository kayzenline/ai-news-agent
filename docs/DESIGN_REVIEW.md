## 2. P1：核心结果与交付缺口

### R1：来源失败可能被解释为“没有新闻”

**证据**：[news_tools.py:165](../app/tools/news_tools.py#L165) 将来源异常汇成文本；[registry.py:71](../app/tools/registry.py#L71) 在函数返回字符串时仍记工具成功；[brief.py:48](../app/brief.py#L48) 接受空条目；[service.py:166](../app/service.py#L166) 直接将空草稿记 `no_news`。

**复核**：没有任何检索证据的空草稿也通过校验；将所选来源全部替换为抛异常的函数，注册表返回 `(True, "errors: ...")`。现有 `test_zero_items_is_no_news_and_not_emailed` 只验证空条目结果，不验证检索前提。

**影响**：未检索、全来源故障和确实没有新增可能展示相同结果；来源故障还可能不计入 Agent 的工具失败早停。

**建议与验收**：保留可正常为空的内容契约，但增加来源成功/空结果/失败及话题覆盖账本。无必要成功检索不得判 `no_news`；全部失败记明确失败，部分成功且有合格条目应展示覆盖不足。用零检索、全失败、正常空结果、部分失败四个固定用例验收。对应设计 §4、§9、§11。

### R2：日期限制没有成为发布条件

**证据**：[news_tools.py:31](../app/tools/news_tools.py#L31) 只检查日期下界，没有未来上界；[brief.py:31](../app/brief.py#L31) 的校验不检查证据日期或草稿中的“今日发布”。

**复核**：2001 年、2099 年和未知日期的证据均可通过草稿校验。旧日期通过校验器并不表示所有搜索适配器都会返回旧文；问题是直接抓取、来源异常时间和模型表述没有发布侧约束。

**影响**：有真实链接的旧消息或未来时间仍可成为“每日新闻”。未知日期的来源标签已经展示，不能把这一展示能力也写成未实现。

**建议与验收**：区分来源发布时间、事件时间与抓取时间；未来时间拒绝或标异常，旧材料仅作背景，未知日期不得宣称今日发布。HN 提交时间不能代替原文发布时间。用已知旧文、未来日期、未知日期与同日新文验收。对应设计 §4、§9。

### R3：数据库提交失败会污染去重历史

**证据**：[service.py:161](../app/service.py#L161) 在提交 Brief 前发布正文和历史；[service.py:181](../app/service.py#L181) 才提交数据库；[service.py:139](../app/service.py#L139) 下一轮从文件历史建立已发布 URL 集合。

**复核**：临时库中注入发布后提交异常，得到 Brief 行数 0、历史文件数 1；重试同条新闻时被判 `already published`，最终 `validation_failed`。现有历史隔离测试没有覆盖该提交失败窗口。

**影响**：用户没有可查看的成功简报，该新闻却已被去重。正文、历史、草稿/证据 JSON 各自落盘，也不是整体原子发布。

**建议与验收**：以已提交的简报记录作为发布事实来源，历史视图可重建；设计文件准备、DB 提交与恢复对账协议，清理或回滚未提交历史。注入发布各步、DB commit 前后故障，保证重试可发布且账本/文件一致。对应设计 §7、§8。

### R4：同一投递记录并发执行会重复发信

**证据**：[service.py:217](../app/service.py#L217) 只跳过 `sent`；[service.py:224](../app/service.py#L224) 设置 `sending` 前没有原子领取；[main.py:132](../app/main.py#L132) 重试路由可再次调用 `deliver`。

**复核**：首个模拟 SMTP 调用阻塞时，第二个线程对同一 Delivery 再次执行；共发送两次，最终 `sent/attempts=2`。`test_delivery_is_separate_from_generation` 只覆盖顺序重试对 `sent` 的跳过。

**影响**：唯一投递行和稳定 Message-ID 无法阻止并发邮件发送；连点或生成期间重试就能触发，不限于进程崩溃的不确定窗口。

**建议与验收**：用数据库条件更新原子领取允许重试的状态；已 `sending` 的记录不得再次领取；保留崩溃后的 `unknown` 显式重发语义。两个并发调用应只有一个 SMTP 调用。该修复仍不构成端到端 exactly-once。对应设计 §10.2。

### R5：失败定时记录阻止当天恢复执行

**证据**：[service.py:46](../app/service.py#L46) 对已存在幂等键无论终态都返回旧 Run；容量拒绝也保存带键失败记录；[scheduler.py:84](../app/scheduler.py#L84) 只判断当天键是否存在。

**复核**：队列满时产生 scheduled failed，容量恢复后补跑列表仍为空，同键提交仍返回旧失败；初始化失败行为相同。现有 `test_business_date_and_catch_up_use_user_timezone` 明确按“有记录便不补跑”断言，尚未覆盖可恢复失败策略。

**影响**：短暂故障会让用户错过当天简报；“每日一个逻辑 run”目前等价于“每日最多一次受理尝试”，中断也不能自动恢复。后续日期使用新键，仍可正常执行。

**建议与验收**：保留一个逻辑 run，引入 attempt 与有界重试策略，区分成功、无新闻、运行中和可重试失败；容量恢复及重启后在窗口内恢复尝试。验收不并发重复执行，同时不把失败当作当天完成。对应设计 §7、§10.1。

## 3. P2：边界与扩展尚未完善

### R6：更新标志不能证明有新事实

[brief.py:70](../app/brief.py#L70) 仅要求 `update` 有非空 delta；[brief.py:95](../app/brief.py#L95) 对更新跳过历史 URL 拒绝。复核中，已发布 URL 加任意 delta、没有新证据或有效事件关联即可通过；一个普通条目混入新 URL 也可通过历史规则。

应建立旧简报与事件关联，比较新旧证据，允许不确定结果但不能把字段存在当作事件雷达完成。验收公告、转载、实质更新及伪更新；事实支持与订阅相关性另建人工样本集。对应设计 §4、§8、§13。

### R7：不合法字段或 URL 可能跳过工具纠错流程

[brief.py:70](../app/brief.py#L70) 的 `change_type` 未先验证类型：非空列表/对象会抛 `TypeError`，空列表会被当成 `new`；[agent.py:92](../app/agent.py#L92) 未捕获 validator 异常，无法进入修订。

[evidence.py:22](../app/evidence.py#L22) 访问非法端口会抛 `ValueError`；搜索结果中的这类 URL 可以进入证据库，随后 [brief.py:90](../app/brief.py#L90) 规范化引用 URL 时直接抛异常，而非返回校验错误。已有坏 URL 时，后续正常抓取的证据匹配也可抛异常；[registry.py:76](../app/tools/registry.py#L76) 的证据注入位于工具执行异常处理之外。`call_key` 已捕获非法端口的 `ValueError` 并回退参数序列化，不属于此处逃逸路径。合法 IPv6 规范 URL 还丢失主机方括号。上述行为已离线复核。

应让所有草稿字段严格校验并返回错误列表，URL 规范化对无效输入产生受控错误且正确保留 IPv6；验收这些输入能反馈给模型修改，而非直接失败。对应设计 §4–6。

### R8：软期限、结束原因和资源预算不完整

[agent.py:73](../app/agent.py#L73) 只在调用前检查期限；最终响应回来后可直接结束。复核中模型耗时超过期限后仍为 `model_finished`。这既不是硬截止，也未做到每次响应后的软期限复查。[providers.py:42](../app/llm/providers.py#L42) 对 `content_filter` 等未知结束原因映成正常 `end`，原始诊断丢失。

总 token、文件读取、草稿/磁盘、搜索来源下载和上下文大小均无完整预算；现有输出截断及 `fetch_url` 2 MB 不能覆盖这些入口。应保留原始结束原因、复查响应时间并按剩余预算约束 I/O/重试；用超时最终响应、过滤响应和超大输入验收。对应设计 §5、§6、§11。

### R9：补跑窗口和事件时间存在边界

[scheduler.py:74](../app/scheduler.py#L74) 只构造当天到期时刻。复核 Sydney 用户 23:30 到期、翌日 00:20 重启，虽距漏跑仅 50 分钟且窗口 6 小时，仍不会补跑。[db.py:71](../app/db.py#L71) 等字段使用无时区 `datetime.now()`，页面直接显示宿主时间。

应按补跑时间窗口覆盖可能的前一业务日，并为超窗漏跑留记录；事件时间统一 UTC，展示时明确用户时区。用跨午夜、DST 重复/跳过与宿主时区变化验收。当天业务日期和时区 cron 已实现，不应回退成“没有时区支持”。对应设计 §7、§10.1。

### R10：投递挂起与 Run 终态缺少恢复闭环

[service.py:181](../app/service.py#L181) 提交 Brief+Delivery 后发送，最后才由 [service.py:81](../app/service.py#L81) 更新 Run。崩溃可留下成功 Brief、甚至已发邮件，而 Run 重启显示 `interrupted`。[service.py:237](../app/service.py#L237) 启动只处理 `sending`，提交后尚未开始发送的 `pending` 不自动恢复；已离线确认仍保持 pending。

页面可手动重发 `pending/failed/unknown`，并非无法恢复；`not_configured` 补配 SMTP 后没有重发按钮。应提供 pending 扫描/退避与记录对账，并把发送移出生成执行槽。验收提交后发送前、SMTP 返回后 Run 更新前的崩溃边界。对应设计 §7、§10.2。

### R11：证据最终地址与数据迁移尚不完整

[news_tools.py:228](../app/tools/news_tools.py#L228) 跟随重定向后只返回文本；[evidence.py:91](../app/evidence.py#L91) 仍以原请求 URL 存证据和继承搜索日期。应保存请求与最终 URL，并避免继承不匹配页面的时间/标题。验收合法跨站重定向。

[db.py:89](../app/db.py#L89) 只建表补列，没有迁移版本、完整约束/索引升级、正文 hash 或条目索引；SQL 文件也非严格等价。应增加版本迁移和旧数据升级验收，不能把 `create_all` 当成迁移系统。对应设计 §4、§7。

### R12：共享部署和长期数据管理仍是计划

[main.py:51](../app/main.py#L51) 到各资源路由没有登录、对象授权或 CSRF；姓名/订阅会进入模型上下文，trace 与错误没有完整脱敏/保留策略；没有删除用户与关联文件清理、备份恢复或 OS 沙箱。

当前 loopback、staging 权限、HTML 清理与公网抓取检查已经实现，应保留；DNS 检查与连接间窗口仍需出口策略补强。公网查询/抓取也没有个人信息外发限制。共享访问前验收越权、CSRF、注入外发、出口规则和删除/恢复；本机演示保持单进程。对应设计 §12。

## 4. 本次验证与后续验收

本次完整离线回归：`.venv/bin/pytest -q` → **155 passed in 1.57s**。代码与测试保持不变；使用临时目录、临时库、配置 stub 和 mock 复核当前边界，没有真实新闻、模型或邮件调用。

| 临时复核 | 观察结果 |
|---|---|
| 无检索空草稿 / 全来源异常 | 空草稿通过；全失败文本仍记工具成功 |
| 旧/未来/未知日期 | 草稿校验均通过 |
| 已发布 URL + 任意 delta | 无新增证据仍通过 |
| 发布后 DB commit 故障 | DB 无 Brief，但去重历史有正文；后续重试被拒绝 |
| 同记录并发 deliver | mock SMTP 发送两次 |
| 定时容量恢复 / 跨午夜 | 已失败键阻止补跑；前一业务日漏跑不扫描 |
| pending 恢复 | 启动恢复不处理，需手动重发 |

建议先落实 R1/R3/R4/R5，再补日期与字段校验、恢复和时间边界；之后使用固定公告/转载/更新样本验收 R6。每项修复加入针对触发条件的回归测试，不能仅重跑当前绿色套件就标为解决。
